## Summary

CI checks the code; it never touches GCP. There are no cloud credentials in GitHub, no `plan` and no `apply`. `apply` and `destroy` run from the laptop only.

Two workflows run on pull requests to `main` and on pushes to `main`, each only when its own files change:

- **Terraform checks:** formatting, validation and TFLint, in one job.
- **Python tests:** pytest against the dummy data.

All tool versions are pinned, and the workflows' GitHub token is read-only.

## Workflows

| File                                     | Runs when these change                                          | Steps                                                                                   |
| ---------------------------------------- | --------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| `.github/workflows/terraform-checks.yml` | `terraform/**`, `.tflint.hcl`, the workflow file                | Checkout, install Terraform, `fmt`, `init`, `validate`, install TFLint, `tflint --init`, `tflint` |
| `.github/workflows/python-tests.yml`     | `terraform/modules/content_pipeline/function/**`, `tests/**`, `data/dummy/**`, `pyproject.toml`, the workflow file | Checkout, install Python, install dependencies, `pytest` |

### Terraform checks: what each step catches

| Step | Command                                         | Catches                                                                 | Needs GCP |
| ---- | ----------------------------------------------- | ----------------------------------------------------------------------- | --------- |
| 1    | `terraform fmt -check -recursive`               | Code not in the standard layout (indentation, alignment)                | No        |
| 2    | `terraform init -backend=false` (in `deployment/`) | Downloads providers and loads the module; skips the state bucket     | No        |
| 3    | `terraform validate`                            | Syntax errors, wrong argument names, wrong types, broken references     | No        |
| 4    | `tflint --init`                                 | Downloads the TFLint plugins listed in `.tflint.hcl`                    | No        |
| 5    | `tflint --recursive`                            | Unused variables, missing version constraints, naming, invalid GCP values | No      |

**Terraform background:**

- **`fmt -check`:** reports files that `terraform fmt` would change, and fails, instead of changing them. CI should never rewrite code.
- **`init -backend=false`:** `validate` needs the providers and the module loaded, but not the state. Skipping the backend means no credentials are needed.
- **`validate` on the deployment:** the deployment calls the module, so one `validate` checks both.
- **What `validate` cannot catch:** values that are valid Terraform but invalid in GCP, such as a misspelt region or role name. TFLint's `google` ruleset catches some of them; the rest surface at `apply`.

## Reasoning

### S7.1: offline checks only

| Option                               | What it adds                                   | Verdict  | Why                                                                                  |
| ------------------------------------ | ---------------------------------------------- | -------- | ------------------------------------------------------------------------------------ |
| **Offline checks**                   | Format, validation, lint, unit tests            | Chosen   | No secrets in GitHub. Pull requests from forks work. Nothing in CI can change the cloud. |
| `plan` on pull requests              | Shows the infrastructure change in the pull request | Rejected | Needs keyless login (Workload Identity Federation), a CI service account, read access to Part A's state bucket and the project ID as a secret. Several new parts, mostly in Part A, for a single-maintainer demo. |
| `apply` from CI                      | Deploys on merge                               | Rejected | The demo is built and destroyed by hand (D1.3); automatic deploys would add cost and risk. |

- **Optional extension:** `plan` on pull requests is the natural next step, and the README can name it as such.

### S7.2: one job for Terraform

- **Readable:** one job, five steps, top to bottom.
- **Fast enough:** the whole job takes about a minute; splitting it into parallel jobs would save seconds and repeat the checkout and install steps.
- **Fails at the first problem:** an unformatted file stops the job before validation. Fix, push, repeat.

### S7.3: TFLint rules

**Background:** TFLint is a linter for Terraform. `terraform validate` checks that the code is valid; TFLint checks that it is good. Rules come in **rulesets** (plugins), configured in `.tflint.hcl` at the repository root.

| Ruleset     | Setting                                                     | Examples of what it catches                                           |
| ----------- | ----------------------------------------------------------- | --------------------------------------------------------------------- |
| `terraform` | `preset = "recommended"`                                     | Unused variables and locals, missing provider version constraints, deprecated syntax |
| `terraform` | Plus `terraform_naming_convention`                           | Names that are not snake_case (D7.5)                                  |
| `terraform` | Plus `terraform_documented_variables`, `terraform_documented_outputs` | Variables and outputs without a `description`                |
| `google`    | Enabled, without deep checking                              | Invalid values for some GCP arguments                                  |

- **Why not `preset = "all"`:** it includes `terraform_standard_module_structure`, which expects a `main.tf` in every module. The module splits its resources by topic instead (S6.3). Turning that rule off by hand would need an explanation; picking the rules on top of `recommended` needs none.
- **Why no deep checking:** the `google` ruleset can call the GCP API to check values (deep checking), but that needs credentials (S7.1).
- **`--recursive`:** lints the module and the deployment in one run.

### S7.4: triggers

- **Pull requests to `main`:** the checks run before a merge.
- **Pushes to `main`:** confirms that `main` itself is clean after the merge.
- **Path filters:** a README change does not start the Terraform workflow. Fewer runs, faster feedback.
- **Merge rule:** branch protection on `main` can require both workflows to pass. This is a GitHub setting, not code; the README notes it.

### S7.5: read-only token

- **What it is:** GitHub gives each workflow run a token (`GITHUB_TOKEN`). Its default permissions can include write access to the repository.
- **Setting:** `permissions: contents: read` at the top of each workflow. The checks only read code.
- **Same principle as step 4:** least privilege, applied to CI.

### S7.6: pinned versions

| Item                               | Pinned where                                     | Why                                                                     |
| ---------------------------------- | ------------------------------------------------ | ----------------------------------------------------------------------- |
| Terraform                          | `terraform_version` input of `hashicorp/setup-terraform` | Same version locally and in CI; matches `required_version` (S2.6) |
| TFLint                             | `tflint_version` input of `terraform-linters/setup-tflint` | A new TFLint release cannot break CI unexpectedly            |
| TFLint plugins                     | `version` in each `plugin` block of `.tflint.hcl` | Required by TFLint; also keeps the rules stable                       |
| GitHub Actions                     | Major version tag (for example `@v4`)            | Receives fixes without breaking changes                                |

- **Exact numbers:** set at implementation time from the current releases.
- **Stricter option:** pinning actions to a full commit SHA protects against a compromised tag. Common in production; noted in the README as a known trade-off.
- **`tflint --init` and rate limits:** plugin downloads come from GitHub. Passing `GITHUB_TOKEN` to that step avoids anonymous rate limits.

### S7.7: Python tests in CI

- **Why:** the function is the only custom code that transforms data. Its unit tests (D4.16) run in seconds against the committed dummy data.
- **Why a separate workflow:** different tools, different triggers. A SQL or Terraform change does not need pytest, and a Python change does not need TFLint.

### S7.8: local checks

- **Same commands:** the README lists the five Terraform commands and `pytest`, so a failure in CI can be reproduced on the laptop.
- **Pre-commit hooks:** optional. They run the same checks automatically before each commit, but add another tool and configuration file to explain.

## Not included

| Security scanner (Trivy, Checkov)    | Flags insecure settings (for example public buckets) | Many findings would need suppressing with reasons; optional extension        |
